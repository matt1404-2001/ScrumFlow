| **CU-04** | **Gestionar equipo Scrum y acuerdos** |
| **Fecha de creación** | 05/10/2026 |
| **Versión** | 1 |
| **Autor** | Equipo |
| **Actores** | **Administrador del proyecto:** gestiona integrantes, permisos técnicos, responsabilidades Scrum y Definition of Done. **Usuario invitado:** acepta o rechaza una invitación. **Miembro del proyecto:** consulta el equipo y los acuerdos. **Sistema:** aplicación web, API y base de datos. |
| **Requisitos previos** | 1. Los actores deben haber iniciado sesión. 2. El proyecto debe existir y estar seleccionado. 3. Para administrar el equipo o los acuerdos, el usuario debe ser administrador del proyecto. 4. La persona invitada debe poseer una cuenta registrada. 5. La API y la base de datos deben estar disponibles. |
| **Objetivos asociados** | 1. Incorporar usuarios registrados al equipo mediante invitaciones internas. 2. Administrar integrantes y permisos de administración. 3. Asignar las responsabilidades Product Owner, Scrum Master y Developer. 4. Definir y mantener la Definition of Done del proyecto. |
| **Descripción** | Este caso de uso permite consultar y administrar el equipo de un proyecto Scrum. Un administrador puede invitar usuarios registrados, administrar integrantes, asignar responsabilidades Scrum y definir la Definition of Done. Las invitaciones deben ser aceptadas antes de crear una membresía y no asignan responsabilidades Scrum automáticamente. Los permisos técnicos de administrador se mantienen separados de las responsabilidades Product Owner, Scrum Master y Developer. |
| **Entradas** | **Proporcionadas por los actores:** correo del usuario invitado, aceptación o rechazo de la invitación, responsabilidades Scrum, permiso de administrador, criterios de la Definition of Done y acción solicitada.  **Internas del sistema:** usuarios registrados, integrantes, invitaciones pendientes, administradores, responsabilidades actuales, trabajo asignado y Sprint vigente.  **Disparador:** el caso comienza cuando un administrador accede al área “Equipo” o un usuario consulta una invitación pendiente. |
| **Secuencia normal** | 1. El administrador accede al área “Equipo”. 2. El sistema muestra integrantes, administradores, responsabilidades Scrum, invitaciones pendientes y Definition of Done. 3. El administrador selecciona “Invitar integrante” e introduce el correo registrado del usuario. 4. El sistema normaliza el correo y comprueba que la cuenta exista y no pertenezca al proyecto. 5. El administrador confirma la invitación. 6. El sistema crea una invitación interna pendiente. 7. El usuario invitado inicia sesión y consulta la invitación. 8. El usuario selecciona “Aceptar”. 9. El sistema registra al usuario como miembro sin asignarle responsabilidades Scrum ni permisos de administrador. 10. El administrador asigna posteriormente las responsabilidades que correspondan. 11. El sistema guarda los cambios y muestra el equipo actualizado. 12. El caso de uso finaliza correctamente. |
| **Secuencias alternativas y excepciones** | **A1. Rechazar una invitación:** el usuario selecciona “Rechazar”; el sistema cierra la invitación sin crear una membresía.  **A2. Asignar responsabilidades Scrum:** el administrador selecciona uno o varios integrantes y asigna Product Owner, Scrum Master o Developer; el sistema impide que existan simultáneamente dos Product Owners o dos Scrum Masters.  **A3. Administrar permisos técnicos:** un administrador concede o retira el permiso de administración a otro miembro, siempre que el proyecto conserve al menos un administrador.  **A4. Actualizar la Definition of Done:** el administrador agrega, modifica, ordena o elimina criterios; los cambios se aplican a futuros Sprints y no alteran la copia conservada por un Sprint ya activado.  **A5. Retirar un integrante:** el administrador selecciona un miembro; si tiene trabajo activo, debe reasignarse antes de retirarlo. Sus participaciones históricas se conservan.  **A6. Usuario inexistente o ya relacionado:** si el correo no pertenece a una cuenta, ya es miembro o posee una invitación pendiente, el sistema no crea otra invitación e informa la situación.  **A7. Operación no autorizada o error del sistema:** el servidor rechaza la operación, no guarda cambios parciales e informa que no fue posible completarla. |
| **validaciones** | 1. Solo un administrador puede enviar invitaciones, administrar integrantes, asignar responsabilidades, conceder permisos técnicos o modificar la Definition of Done. 2. El correo invitado debe pertenecer a una cuenta registrada y no puede tener una membresía o invitación pendiente en el mismo proyecto. 3. Una invitación debe ser aceptada antes de crear la membresía y no asigna automáticamente responsabilidades Scrum. 4. El proyecto debe conservar al menos un administrador. 5. Solo puede existir un Product Owner y un Scrum Master, mientras que puede haber varios Developers y una persona puede asumir más de una responsabilidad. 6. Antes de activar un Sprint debe existir un Product Owner, un Scrum Master, al menos un Developer y una Definition of Done con al menos un criterio. 7. Un integrante con trabajo activo debe ser reemplazado o tener su trabajo reasignado antes de retirarse; sus registros históricos no deben eliminarse. 8. Las modificaciones de la Definition of Done no deben alterar la versión conservada por Sprints previamente activados. |
| **Mensaje de Sistema** | 1. Invitación enviada: “Invitación creada correctamente”. 2. Invitación aceptada: “Ahora formas parte del proyecto”. 3. Invitación rechazada: “Invitación rechazada”. 4. Usuario inexistente: “No existe una cuenta registrada con ese correo”. 5. Usuario ya relacionado: “El usuario ya pertenece al proyecto o tiene una invitación pendiente”. 6. Cambios guardados: “Equipo y acuerdos actualizados correctamente”. 7. Configuración incompleta: “El proyecto necesita un Product Owner, un Scrum Master, al menos un Developer y una Definition of Done”. 8. Error general: “No fue posible completar la operación. Inténtalo nuevamente”. |
| **Salida de Sistema** | 1. Invitación creada, aceptada o rechazada según la acción realizada. 2. Lista de integrantes, administradores y responsabilidades actualizada. 3. Definition of Done actualizada para futuros Sprints. 4. Configuración del equipo disponible para validar posteriormente la activación del Sprint. |
