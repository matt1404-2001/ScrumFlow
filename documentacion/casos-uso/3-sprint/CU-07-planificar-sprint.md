| **CU-07** | **Planificar Sprint** |
| **Fecha de creación** | 06/10/2026 |
| **Versión** | 1 |
| **Autor** | Equipo |
| **Actores** | **Scrum Team:** colabora en la definición del Sprint Goal y la selección del trabajo. **Administrador del proyecto:** confirma la activación del Sprint. **Sistema:** aplicación web, API y base de datos. |
| **Requisitos previos** | 1. El usuario debe haber iniciado sesión y ser miembro del proyecto. 2. No debe existir otro Sprint en estado Borrador, Activo o En cierre. 3. El Product Backlog debe contener elementos disponibles. 4. La API y la base de datos deben estar disponibles. |
| **Objetivos asociados** | 1. Crear y preparar un Sprint en estado Borrador. 2. Definir el Sprint Goal y las fechas del Sprint. 3. Seleccionar elementos del Product Backlog. 4. Activar el Sprint cuando la planificación esté completa. |
| **Descripción** | Este caso de uso permite al Scrum Team preparar un Sprint definiendo su objetivo, fechas y elementos seleccionados del Product Backlog. La planificación puede guardarse incompleta como borrador, pero solo puede activarse cuando cumple las condiciones requeridas. Al activarse, los elementos seleccionados forman el Sprint Backlog y quedan disponibles para administrar su ejecución. Las fechas individuales, responsables, estados, checklist, comentarios e impedimentos se gestionan posteriormente dentro del Sprint activo. |
| **Entradas** | **Proporcionadas por el usuario:** Sprint Goal, fecha de inicio, fecha de finalización, elementos seleccionados y acción de guardar o activar.  **Internas del sistema:** Product Goal, Definition of Done, equipo, responsabilidades Scrum, Product Backlog, estimaciones y Sprints existentes.  **Disparador:** el caso comienza cuando un miembro accede al área “Sprint” y selecciona “Planificar Sprint”. |
| **Secuencia normal** | 1. El miembro selecciona “Planificar Sprint”. 2. El sistema comprueba que no exista otro Sprint sin finalizar y muestra el Product Goal, la Definition of Done y los elementos disponibles. 3. El Scrum Team define el Sprint Goal y las fechas del Sprint. 4. Los Developers seleccionan los elementos que consideran realizables. 5. El sistema muestra los elementos seleccionados y la suma de sus estimaciones. 6. El miembro guarda la planificación como Borrador. 7. El equipo revisa la planificación y un administrador selecciona “Activar Sprint”. 8. El servidor valida el equipo, los objetivos, las fechas, la Definition of Done y los elementos seleccionados. 9. El sistema conserva una copia de la Definition of Done vigente y asocia los elementos con el Sprint. 10. El sistema cambia el Sprint a estado Activo y coloca los elementos en estado Pendiente. 11. La aplicación muestra el tablero del Sprint y actualiza la guía del proyecto. 12. El caso de uso finaliza correctamente. |
| **Secuencias alternativas y excepciones** | **A1. Guardar planificación incompleta:** el usuario guarda el Sprint como Borrador; el sistema conserva la información e indica qué condiciones faltan para activarlo.  **A2. Modificar la planificación:** mientras el Sprint permanezca en Borrador, los miembros pueden cambiar el objetivo, las fechas o los elementos seleccionados.  **A3. Elemento no preparado:** si un elemento carece de título, descripción o estimación, puede permanecer en el Product Backlog, pero no utilizarse para activar el Sprint.  **A4. Fechas inválidas:** si la fecha final es anterior a la inicial o la duración supera cuatro semanas, el sistema rechaza la activación y solicita corregirlas.  **A5. Configuración incompleta:** si faltan Product Goal, Definition of Done, Product Owner, Scrum Master o Developers, el sistema mantiene el Sprint como Borrador e indica qué debe configurarse.  **A6. Elemento no disponible:** si un elemento fue retirado o asociado con otro Sprint no finalizado, el sistema lo excluye de la selección e informa la situación.  **A7. Activación no autorizada o error del sistema:** el servidor no activa el Sprint, conserva el Borrador y muestra el error correspondiente. |
| **validaciones** | 1. El usuario debe ser miembro para participar en la planificación y administrador para activar el Sprint. 2. Solo puede existir un Sprint no finalizado por proyecto. 3. El Sprint Goal, las fechas y al menos un elemento son obligatorios para activar el Sprint. 4. La fecha final no puede ser anterior a la inicial y la duración no puede superar cuatro semanas o 28 días naturales. 5. Antes de la activación deben existir Product Goal, Definition of Done, exactamente un Product Owner, exactamente un Scrum Master y al menos un Developer. 6. Cada elemento seleccionado debe estar activo, disponible y contener título, descripción y estimación. 7. Un elemento no puede pertenecer simultáneamente a dos Sprints no finalizados. 8. Las fechas individuales, responsables y demás datos de ejecución no se asignan durante esta función. 9. La activación debe asociar todos los elementos y conservar la Definition of Done como una única operación. |
| **Mensaje de Sistema** | 1. Borrador guardado: “Planificación del Sprint guardada”. 2. Activación exitosa: “Sprint activado correctamente”. 3. Duración inválida: “El Sprint no puede durar más de cuatro semanas”. 4. Elemento no preparado: “Todos los elementos seleccionados deben tener descripción y estimación”. 5. Configuración incompleta: “Completa la configuración del equipo, los objetivos y la Definition of Done”. 6. Sprint existente: “Ya existe un Sprint sin finalizar en este proyecto”. 7. Error general: “No fue posible guardar o activar el Sprint. Inténtalo nuevamente”. |
| **Salida de Sistema** | 1. Sprint guardado como Borrador o cambiado a Activo. 2. Sprint Goal, fechas y elementos seleccionados registrados. 3. Sprint Backlog formado por los elementos asociados. 4. Copia de la Definition of Done conservada para el Sprint activo. 5. Tablero inicial disponible con los elementos en estado Pendiente. |
