| **CU-08** | **Gestionar trabajo del Sprint** |
| **Fecha de creación** | 06/10/2026 |
| **Versión** | 1 |
| **Autor** | Equipo |
| **Actores** | **Miembro del proyecto:** consulta y actualiza el trabajo del Sprint. **Developers:** ejecutan el trabajo y confirman el cumplimiento de la Definition of Done. **Administrador del proyecto:** puede iniciar el cierre del Sprint. **Sistema:** aplicación web, API y base de datos. |
| **Requisitos previos** | 1. El usuario debe haber iniciado sesión y ser miembro del proyecto. 2. Debe existir un Sprint Activo. 3. El elemento debe pertenecer al Sprint. 4. La API y la base de datos deben estar disponibles. |
| **Objetivos asociados** | 1. Administrar el trabajo mediante un tablero. 2. Asignar responsables, estados y fechas a los elementos del Sprint. 3. Registrar checklist, comentarios e impedimentos. 4. Confirmar la Definition of Done antes de terminar un elemento. 5. Consultar el avance e iniciar el cierre del Sprint. |
| **Descripción** | Este caso de uso permite gestionar el trabajo de un Sprint Activo desde un tablero con los estados Pendiente, En progreso y Terminado. Los miembros pueden abrir cada tarjeta y administrar responsable, fechas, checklist, comentarios e impedimentos. Para mover un elemento a Terminado se debe confirmar la Definition of Done conservada por el Sprint. Al concluir la ejecución, un administrador puede iniciar el cierre y bloquear el tablero para realizar la Review y la Retrospectiva. |
| **Entradas** | **Proporcionadas por el usuario:** elemento seleccionado, responsable, estado, fecha de inicio, fecha límite, checklist, comentario, impedimento y acción solicitada.  **Internas del sistema:** Sprint Goal, fechas del Sprint, Definition of Done, integrantes, elementos asociados y estado actual del tablero.  **Disparador:** el caso comienza cuando un miembro accede al Sprint Activo o abre una tarjeta del tablero. |
| **Secuencia normal** | 1. El miembro accede al Sprint Activo. 2. El sistema muestra el Sprint Goal, el avance y el tablero organizado por estados. 3. El miembro abre una tarjeta. 4. El sistema muestra su información y los campos de ejecución. 5. El miembro asigna un responsable, registra fechas y actualiza checklist, comentarios o estado. 6. La aplicación valida la información y envía los cambios al servidor. 7. El servidor confirma que el Sprint continúe Activo y guarda la actualización. 8. Cuando el miembro selecciona Terminado, el sistema muestra la Definition of Done del Sprint. 9. El miembro confirma el cumplimiento de sus criterios. 10. El sistema registra quién realizó la confirmación y cuándo, mueve la tarjeta a Terminado y actualiza el avance. 11. La aplicación muestra el tablero actualizado y el caso finaliza correctamente. |
| **Secuencias alternativas y excepciones** | **A1. Cambiar el estado:** el miembro mueve una tarjeta entre Pendiente y En progreso; el sistema guarda el cambio sin solicitar la Definition of Done.  **A2. Fechas inválidas:** si la fecha inicial es posterior a la fecha límite o alguna queda fuera del Sprint, el sistema rechaza el cambio y solicita corregirlas.  **A3. Responsable no válido:** si la persona seleccionada no pertenece al proyecto, el sistema no guarda la asignación.  **A4. Definition of Done no confirmada:** si el usuario no confirma todos los criterios, el elemento conserva su estado anterior y no forma parte del incremento.  **A5. Reabrir un elemento:** al mover una tarjeta desde Terminado, el sistema elimina su confirmación vigente y deja de considerarla parte del incremento.  **A6. Registrar o resolver un impedimento:** el miembro agrega la descripción del impedimento o lo marca como resuelto; el sistema actualiza la tarjeta y la guía del proyecto.  **A7. Iniciar el cierre:** un administrador confirma la acción; el sistema cambia el Sprint a En cierre, bloquea el tablero y habilita la Sprint Review.  **A8. Sprint bloqueado o error del sistema:** si el Sprint ya no está Activo o ocurre un error, el sistema conserva la información anterior y rechaza la actualización. |
| **validaciones** | 1. El usuario debe mantener una sesión válida, ser miembro del proyecto y trabajar sobre un Sprint Activo. 2. El responsable, cuando se asigne, debe ser integrante del proyecto. 3. Las fechas son opcionales, pero deben encontrarse dentro del Sprint y la fecha inicial no puede ser posterior a la fecha límite. 4. El estado debe ser Pendiente, En progreso o Terminado. 5. Checklist, comentarios e impedimentos deben contener texto válido y conservar su autor y fecha cuando corresponda. 6. Marcar un elemento como Terminado requiere confirmar la Definition of Done y registrar quién realizó la confirmación. 7. Reabrir un elemento elimina su confirmación vigente y lo excluye del incremento. 8. Solo un administrador puede iniciar el cierre; después de hacerlo no se permiten cambios operativos en el tablero. |
| **Mensaje de Sistema** | 1. Actualización exitosa: “Trabajo del Sprint actualizado”. 2. Fechas inválidas: “Las fechas deben encontrarse dentro del Sprint”. 3. Responsable inválido: “Selecciona un integrante del proyecto”. 4. Definition of Done pendiente: “Confirma la Definition of Done antes de terminar el elemento”. 5. Impedimento registrado: “Impedimento registrado correctamente”. 6. Cierre iniciado: “El Sprint entró en cierre. El tablero quedó bloqueado”. 7. Operación no permitida: “El Sprint ya no admite cambios en el tablero”. 8. Error general: “No fue posible actualizar el trabajo. Inténtalo nuevamente”. |
| **Salida de Sistema** | 1. Tablero actualizado con responsables, estados y fechas. 2. Checklist, comentarios e impedimentos registrados. 3. Avance del Sprint e incremento actualizado. 4. Confirmación de la Definition of Done conservada cuando corresponda. 5. Sprint cambiado a En cierre y tablero bloqueado cuando se inicia el cierre. |
